# E-03.5 · Skills: choosing and writing them

- **Where it sits:** Engineering track › Repo setup for AI
- **Who:** Recommended: all engineering roles
- **Delivery:** Engineering track, session 4; also usable self-serve
- **Time:** 25 min

A skill turns a procedure you keep re-explaining into something the agent loads when it is needed. A third-party skill is also code that runs with your permissions, which most people install without reading.

## Outcomes

A participant can:

- Decide whether something should be a skill, an instruction, a hook or a connector.
- Review a third-party skill before installing it.
- Write a small skill with a description that triggers at the right time.

## Topics

### Required

- What it is: a folder with a `SKILL.md` (name, description, instructions) and optional scripts and reference files, loaded on demand when its description matches the task. The format is an open standard used across tools.
- When to write one: a recurring, bounded procedure such as a review checklist, release notes or a house style. Not for one-off tasks, and not for facts.
- Choosing the mechanism: a skill is how to do a task, an instruction file is an always-on rule, a hook is something that must always happen, a connector gives access to an external system.
- A third-party skill is code you run. Read all of it, scripts included, before installing. Check the source, the licence and whether it is maintained. Pin a version.
- Fewer and better. Each skill costs context and can contradict another.

### Recommended

- The description is the trigger: say what the skill does and when to use it. Keep the body short (under about 500 lines) and move detail into reference files.
- State inputs, outputs and an acceptance check. Test on real cases before sharing.
- Scope and ownership: personal, project (committed), or packaged as a plugin. Each skill has an owner.
- Limit what a skill may do, and whether the model may invoke it on its own.
- A reviewed, pinned copy in the repository versus an auto-updating plugin: choose per skill according to trust.
- Keep the upstream licence next to a copied skill and list third-party skills in one place.

### Optional

- Plugins and marketplaces.
- Evaluating a skill's effect.
- Skills that run in a separate agent context.

## Checkpoint

> Which of these four would you make a skill: the test command, the release checklist, "never edit generated files", access to the issue tracker?

## Practice

Write a 20-line skill for a pull request description in the team's format. Check that it triggers on "write the PR description" and stays quiet otherwise.

## Re-verify before each delivery

- Frontmatter fields, install commands and marketplaces.
