# E-03.2 · Permissions and modes

- **Where it sits:** Engineering track › Repo setup for AI
- **Who:** Required: developers, architects and tech leads, DevOps · Recommended: QA
- **Delivery:** Engineering track, session 2; also usable self-serve
- **Time:** 25 min

Instructions say what an agent should do. Permissions decide what it is able to do. Teams that confuse the two discover the difference at the worst moment.

## Outcomes

A participant can:

- Read a permission configuration and predict whether an action runs, prompts or is blocked.
- Choose a permission mode for a task.
- Say which protections need a rule and which need isolation.

## Topics

### Required

- Three answers for any action: allow, ask, deny. Deny wins. Rules live at several levels: project (shared, committed), local (personal), user, and managed (organization).
- Five capability classes to think in: read, edit, run commands, reach the network, cause external side effects (push, deploy, send).
- Permission modes run from asking for everything, through read-only planning and auto-accepting edits, to a classifier-reviewed automatic mode. Bypassing all checks is for isolated containers only.
- Start narrow and widen deliberately, based on what you find yourself approving again and again.
- Protect secrets files, CI and deployment configuration, the agent's own configuration, and git internals.
- A rule that matches a command's text is not a security boundary. The same command can be spelled many ways. Isolation covers that ([E-03.3](E-03.3-sandboxing-and-isolation.md)).

### Recommended

- Automatic modes: what the classifier blocks by default (force pushes, piping downloads into a shell, production deploys) and what it allows (local edits, and pushes to the repository you are working in). A boundary you state in conversation counts, and can be lost when the conversation is compacted. For a guarantee, write a deny rule.
- Deny rules for what only a human does in this repository, such as publishing or deploying.
- Hooks for deterministic checks: validate before a tool runs, format after an edit, block edits to protected files.
- Team defaults in the committed settings, personal loosening only in local settings, and settings changes reviewed in pull requests.
- A client's managed policy overrides yours.

### Optional

- Managed settings for an organization.
- Permissions for connector and MCP tools.
- Audit logs.
- Permission profiles for unattended and CI runs ([E-08](../E-08-automation-and-operations.md)).

## Checkpoint

> Given this settings file and these four actions, which run, which prompt and which are blocked?

## Practice

Start from read-only. Add the minimum rules needed to let an agent run the test suite and edit one directory. Try to make it push, and observe what stops it.

## Re-verify before each delivery

- Mode names and defaults. In Claude Code the automatic mode is the default for interactive sessions from release 2.1.283.
- Rule syntax and which settings files honour which keys.
