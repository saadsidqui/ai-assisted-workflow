# E-03.6 · Memory, knowledge, specs, state and handoffs

- **Where it sits:** Engineering track › Repo setup for AI
- **Who:** Required: developers, architects and tech leads · Recommended: QA, DevOps · Optional: PM / PO, analysts
- **Delivery:** Engineering track, session 3; also usable self-serve
- **Time:** 25 min

Sessions forget and people rotate. Work that spans more than one session needs its memory in files that any session, tool or colleague can read.

## Outcomes

A participant can:

- Lay out a project directory that separates specification, state, decisions, handoffs and knowledge.
- Write a handoff that a fresh session can continue from.
- Explain why a tool's memory feature is not the source of truth.

## Topics

### Required

- Sessions forget; the repository remembers. Whatever the next session or person needs lives in files.
- A project directory for AI-assisted work (for example `.ai/project/`) holding the brief and specification (what, and how success is judged), the state (where things stand and what is next), decisions (what was chosen and why), handoffs (what happened in a session), and knowledge (curated facts).
- Stable versus volatile: instructions and the specification change rarely and deliberately. State and handoffs change every session.
- A handoff has six parts: goal, what was done, files changed, checks run and their results, open questions, next step. Write it before ending a session or when context runs low.
- A tool's memory is a convenience and, in some tools, local to one machine. It is never the source of truth.
- No secrets, no personal data and no raw transcripts in any of these files.

### Recommended

- A decision log: short, dated records that are not edited once accepted. A later decision supersedes an earlier one.
- Lifecycle and locking: once setup is complete, governance files (instructions, design, specification, skills) change only with explicit human approval. State and handoffs stay writable.
- Session rituals: at the start, read the state and the latest handoff. At the end, update the state and write a handoff.
- Date entries and prune stale knowledge on a schedule.
- A specification format with acceptance criteria ([E-04](../E-04-specs-and-context-engineering.md)).

### Optional

- The issue tracker as the state store.
- Automated indexing and retrieval of project knowledge.
- Memory per sub-agent.
- Shared team memory.

## Checkpoint

> You open a repository someone else's agent worked in yesterday. Which three files do you read first?

## Practice

End a short agent session by writing a handoff. A neighbour starts a new session from that handoff alone and reports what was missing.

## Re-verify before each delivery

- Where each tool stores its automatic memory and how much of it loads.
