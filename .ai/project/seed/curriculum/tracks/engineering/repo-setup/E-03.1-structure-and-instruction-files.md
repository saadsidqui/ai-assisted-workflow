# E-03.1 · Structure and instruction files

- **Where it sits:** Engineering track › Repo setup for AI
- **Who:** Required: developers, architects and tech leads, DevOps · Recommended: QA
- **Delivery:** Engineering track, session 2; also usable self-serve
- **Time:** 20 min

An agent starts every session knowing nothing about the repository. A short, accurate instruction file is the cheapest improvement a team can make, and a long or contradictory one makes things worse.

## Outcomes

A participant can:

- Write a repository instruction file that changes agent behaviour.
- Keep one source of truth across several AI tools.
- Decide which kind of information belongs in which file.

## Topics

### Required

- One shared instruction file at the repository root: `AGENTS.md`, an open convention read by most coding agents. It says what the project is, where things live, how to build, test and lint, which conventions differ from the defaults, what not to touch, and when to stop and ask.
- For Claude Code, a `CLAUDE.md` that contains an `@AGENTS.md` import plus any Claude-only notes. One source of truth, no duplicated rules.
- Short and specific, with a target under about 200 lines. Every line should change behaviour. Prune it regularly.
- An instruction file is guidance, not enforcement ([E-03.2](E-03.2-permissions-and-modes.md)).
- Different kinds of knowledge go in different files: instructions (how to work here), design (constraints and decisions), specification (what to build), state (where things stand). See [E-03.6](E-03.6-memory-knowledge-specs-state-handoffs.md).
- State the precedence in the file: an explicit human instruction, then the instruction file, then the specification, then older documentation. Code and tests outrank stale prose.

### Recommended

- Write for an agent reader: concrete statements that can be verified ("run `npm test` before proposing a commit"), not essays.
- Nested instruction files for subprojects and monorepos, and rules scoped to file paths.
- A personal, uncommitted override file next to the shared one.
- Generate a first draft with the tool's init command, then cut it down by hand.
- Review instruction files in pull requests like code, with one named owner.
- A `DESIGN.md` for architecture and design constraints, or for the design system in interface work.

### Optional

- Pointing other tools' rule files at the same source.
- Organization-level managed instructions.
- A CI check for contradictions and drift.

## Checkpoint

> Here is a 400-line instruction file. Which three sections would you delete first, and why?

## Practice

Draft an instruction file for a sample repository in 25 lines. Swap with a neighbour and find one line that would not change behaviour.

## Re-verify before each delivery

- As of November 2026, Claude Code reads `AGENTS.md` directly only when no `CLAUDE.md` exists (release 2.1.277), and its documentation still recommends the import. Re-check before teaching.
- Which tools read which file names.
